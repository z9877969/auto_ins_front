# scripts/perf — стенд вимірювання Lighthouse

Відтворюваний стенд для порівняння git-ревізій/варіантів білда за
Lighthouse Performance (мобільний пресет). Використовується для кожного
етапу `.claude/performance/plan-v2.md`, щоб не гадати «це шум чи реальний
ефект».

## Що робить

1. Для кожного варіанта з конфіга:
   - або піднімає ізольований `git worktree` на заданому ref і будує його
     там (`npm run build`, node_modules — символьне посилання на основний
     репозиторій, якщо lock-файл розійшовся — білд впаде явно, а не мовчки),
   - або білдить поточний робочий каталог як є (для незакомічених змін);
   - копіює `dist/` в окрему теку (щоб кілька варіантів з одного cwd можна
     було роздавати одночасно різними серверами);
   - за бажанням застосовує `distTransform(dir)` — довільну мутацію копії
     dist перед роздачею (напр. вирізати GTM/Pixel, прибрати частину
     preload-шрифтів).
2. Піднімає для кожного варіанта статичний сервер **з обов'язковим gzip**
   для `.html/.js/.css/.svg/.json` — щоб localhost відповідав тому, що
   Netlify реально віддає в проді. Без цього частина варіантів у минулій
   сесії роздавалась без стиснення (427 КБ проти 147 КБ на головному чанку)
   і числа виявились несумісними.
3. Усі сервери варіантів піднімаються **одночасно** на різних портах.
4. Ганяє `npx lighthouse@12` **послідовно**, round-robin (v0 r1, v1 r1, …,
   v0 r2, …), 2 прогони на варіант за замовчуванням (для фінального заміру
   піднімай `--rounds=5`). Ніколи паралельно — один забруднений прогін уже
   давав викид (42 замість 61 у попередній сесії).
5. Друкує таблицю (варіант | усі бали | медіана | FCP | LCP | TBT | SI |
   CLS) і діагностику останнього прогону кожного варіанта:
   `largest-contentful-paint-element` (з фазами TTFB/Load Delay/Load
   Time/Render Delay), `third-party-summary`, `bootup-time`,
   `mainthread-work-breakdown`, `long-tasks`, `layout-shifts`.

## Запуск

```bash
node scripts/perf/run.mjs <config.mjs> [--rounds=2] [--keep] [--workdir=/path]
```

- `<config.mjs>` — файл з `export default [...]` масивом варіантів, див.
  `scripts/perf/configs/*.mjs`.
- `--rounds` — прогонів lighthouse на варіант (за замовчуванням 2; для
  фінальних цифр, які йдуть у звіт, використовуй `--rounds=5`).
- `--keep` — не видаляти worktree/dist після завершення (для дебагу).
- `--workdir` — куди класти тимчасові файли (за замовчуванням
  `os.tmpdir()/autoins-perf-<timestamp>` — **поза репозиторієм**).

Приклади конфігів у `scripts/perf/configs/`:

- `smoke.mjs` — один локальний варіант, для перевірки, що стенд взагалі
  працює (`--rounds=1`).
- `stage-c.mjs` — порівняння з розділу «Як міряти результат етапу C»:
  база `feat/performance-lcp` (worktree) / поточна гілка / поточна гілка
  без GTM+Pixel. Команда для фінального заміру:
  ```bash
  node scripts/perf/run.mjs scripts/perf/configs/stage-c.mjs --rounds=5
  ```
  Очікування з плану (localhost, тому дивись різницю, не абсолют):
  V0-base-lcp ≈ 39, V-C-current ≈ 61.5, V-C-no-3p ≈ 88.
- `stage-c-fonts.mjs` — A/B/C по кількості preload-шрифтів (4 / 2 / 0),
  усі три — поточна гілка з різною кількістю font-preload лінків:
  ```bash
  node scripts/perf/run.mjs scripts/perf/configs/stage-c-fonts.mjs --rounds=5
  ```
  Дивись на медіану LCP і бала: якщо 2 або 0 не гірші за 4 — preload можна
  скоротити; якщо різниці нема — лишати як є (не вигадувати ефект з шуму).

Формат варіанта:

```js
{ label: 'назва', worktree: '<git ref>' }               // ізольований worktree
{ label: 'назва', local: true }                          // поточний робочий каталог як є
{ label: 'назва', local: true, distTransform: async (distDir) => {} } // + мутація копії dist
```

## Як читати результат

- **Порівнюй різницю між варіантами, не абсолютний бал.** Localhost
  систематично оптимістичніший за прод — нульовий RTT до власних файлів
  (JS/CSS/картинки грузяться миттєво), тоді як сторонні скрипти (GTM,
  Meta Pixel, Clarity) тягнуться по-справжньому через мережу з тим самим
  таймінгом, що й у проді. Це асиметрично завищує бал локально порівняно з
  реальним сайтом. Але **дельта між двома локальними варіантами** (з тим
  самим стендом, тими самими сторонніми скриптами) — валідна оцінка ефекту
  зміни.
- Один прогін lighthouse — шумний (±6–7 балів між прогонами того самого
  білда цілком нормально). Завжди дивись медіану кількох прогонів
  (`--rounds=5` для фінальних цифр), не перший-ліпший результат.
- Ніколи не запускай нічого важкого паралельно з прогонами lighthouse
  (інший білд, тест, тощо) — забруднює вимірювання головного потоку.
- Перед довгим прогоном перевір `ps aux | grep chrome`, що не лишилось
  зомбі-процесів chromium від перерваного попереднього прогону — вони
  тихо їдять CPU і псують наступні виміри.

## Технічна деталь: чому lighthouse.mjs асинхронний

Статичні сервери варіантів піднімаються в тому самому Node-процесі, що й
оркестратор (`run.mjs`) — одна подієва петля на всіх. `lib/lighthouse.mjs`
навмисно запускає `npx lighthouse` через `spawn` (асинхронно), а не
`execFileSync`: синхронний виклик заблокував би подієву петлю на весь час
прогону lighthouse, і сервер варіанта фізично не зміг би відповісти на
запити хрому — самодедлок (порт слухає, з'єднання прийняте ядром, обробити
нікому). Якщо колись знадобиться повністю ізолювати сервери від
оркестратора — піднімати їх окремими дочірніми процесами, а не в процесі
`run.mjs`.

## Залежності стенда

`lighthouse@12` тягнеться через `npx` при кожному запуску (кешується npx
після першого разу). Потрібен `CHROME_PATH` — за замовчуванням
`/snap/bin/chromium` (можна перевизначити змінною середовища перед
запуском). `git worktree` вимагає, щоб ref не був уже зачекаучений в
іншому робочому дереві (крім поточного).
